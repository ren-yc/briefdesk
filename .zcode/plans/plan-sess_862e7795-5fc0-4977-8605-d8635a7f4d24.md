# 含图消息按模型视觉能力路由 — 实现方案

## 一、现状要点（已核实）

- 图片全程以**引用字符串**保活：`InternalMessage.image_urls`（types.py:34）→ `items.image_urls`；图片字节仅在 enrich 阶段瞬时存在（`batch.client.download_media` 下载 → RapidOCR → 丢弃），无缓存无落盘。
- OCR（enrich 槽，`plugins/ocr/plugin.py:54-88`）把识别文本脱敏后以 `[OCR]` 前缀**替换** `msg.content`；classify 引擎（`plugins/classify/engine.py`）只读 `msg.content` 纯文本构建 prompt，**从不看 image_urls**。
- `pipeline.py:258-267 _run_front`：批内 **enrich → classify 串行**（并行的是批与批之间），故 enrich 暂存、classify 消费同一 `BatchContext` 竞态安全。
- AI 通道：`ai_ports.chat(messages: list[dict])` → `ai_provider/engine.py chat()` 直接透传给 `AsyncOpenAI`——**多模态 content parts（`content: [{"type":"text"...},{"type":"image_url"...}]`）无需改任何协议形状即可流过**。
- 入口既有闸门：OCR 未启用时纯占位符图片消息整条过滤（pipeline.py:155-173，可逆不标 processed）。
- 项目无任何 vision/multimodal/base64 现有支持；`announcements.py` 公告机制有 `embedding_unreachable`「失败公告/成功撤销」先例可镜像。

## 二、设计总览

路由判据（用户已选定）：**单模型 + 显式开关 `AI_VISION_ENABLED`（默认 false）**。关闭 = 行为与现状完全一致；开启 = 把 `AI_MODEL` 当视觉模型，含图消息走「OCR 文本 + 图片一并直读」。

**接入范围（用户已确认）**：视觉输入**仅进 classify**（即需求所指"让大模型判断"）。
- dedup 不接入：已有零 AI 确定性机制（image_urls 集合精确短路 + 原文哈希短路）覆盖同图判重大头；候选端是库内历史条目、跨源图片需新修下载管线，成本不成比例；vision classify 产出的 quote/key_info 更准，判重文本通道间接受益。
- merge/post_insert 不接入：判官输入正是 classify 产出的结构化文本，间接受益最直接；且 run 在 `_storage_lock` 内，加网络下载违反「存储相 run 内不碰网络」的管道纪律。
- 「dedup 灰区定向附图判重」列为文档记录的二期演进方向，不在本次实现。
- DB schema、前端媒体代理、raw_messages 语义、`[OCR]` 契约全部不动。

数据通路（复用既有下载，图片在 enrich 一次下载、缩放后随批传递）：

```
enrich(OCR): download_media(bytes) → RapidOCR → [OCR] 替换 content（不变）
                                  └→ vision 开启: Pillow 缩放→JPEG → 暂存 batch.vision_images[(source,msg_id)]
classify: classify_batch(messages, vision_images) → 含图消息构建 multimodal content parts
          （text part=原 user 文本 + 每条含图消息前插入「消息 N 附图」标注 + data:image/jpeg;base64 图片 part）
          → chat() 透传（协议零改动）
```

## 三、分文件改动

1. **`briefdesk/imaging.py`（新模块，核心工具）**
   `downscale_image(data: bytes, *, max_side=1568, quality=85, max_bytes=1_200_000) -> bytes | None`：Pillow 打开 → `ImageOps.exif_transpose` → 转 RGB → 超边长等比缩放（LANCZOS）→ 重编码 JPEG。超 `max_bytes` 先降 quality 再降边长各一次。任何解码/编码异常返回 None（调用方跳过该图）。**输出恒为 JPEG** → classify 侧 data URL 恒为 `data:image/jpeg;base64,...`，无需魔数嗅探。Pillow 已是直接依赖（pyproject.toml:19）。

2. **`briefdesk/config.py`**（AI 字段区 :41-54 附近）
   - `ai_vision_enabled: bool = Field(default=False, alias="AI_VISION_ENABLED")`
   - `ai_vision_max_images: int = Field(default=4, alias="AI_VISION_MAX_IMAGES", ge=1, le=20)`（单条消息随请求附图上限）
   设置 UI 经 `_CORE_UI`（routes_settings_env.py:45-77）加两条 label/hint，schema 自动发现，持久化走既有暂存链。

3. **`briefdesk/types.py`**（BatchContext :231-252）
   新字段 `vision_images: dict[tuple[str, str], list[bytes]] = field(default_factory=dict)`——键 `(source, msg_id)`（与 processed/raw 复合键同口径），值为缩放后 JPEG 字节列表；enrich 写、classify 读、批结束即弃。按 msg 身份（非列表下标）作键，`_split_retry` 切片递归无需搬移。

4. **`briefdesk/plugins/ocr/plugin.py`（enrich 写入点）**
   `run` 中下载成功后（**OCR 调用之前**）执行：若 `config.ai_vision_enabled`，对每张图 `downscale_image`，非 None 者收进 `batch.vision_images[(msg.source, msg.msg_id)]`。要点：
   - stash 在 OCR 之前/独立于 OCR 结果——OCR 抛错或无文字时图片仍可送模型；
   - vision 关闭时整段跳过（零额外内存、零行为变化）；
   - 下载失败（MediaError）维持现状跳过该条，自然无 stash → classify 对该条纯文本降级。

5. **`briefdesk/plugins/classify/plugin.py:38-40`**
   `batch.outcomes = await self._classify_batch(batch.messages, vision_images=batch.vision_images)`；`__init__` 的 Callable 类型标注同步更新。

6. **`briefdesk/plugins/classify/engine.py`（消费点 + 兜底）**
   - `classify_batch(messages, vision_images=None)`（默认 None，既有调用/测试零破坏）；`_split_retry` 透传同一 dict。
   - `_group_messages` 增加 per-msg `"images": vision_images.get((msg.source or "", msg.msg_id)) or []`。
   - 新增 `_build_image_parts(groups) -> list[dict]`：按消息序遍历，每条取前 `config.ai_vision_max_images` 张，**单请求图片总预算 `_MAX_IMAGES_PER_REQUEST = 12`**（超预算的消息该轮只发 OCR 文本，DEBUG 记录）；每条含图消息前插 text part「【消息 N 附 n 张图片】」，段首放一句说明 text part（要求结合图片与文本综合判断）。**不改 `_PROMPT_TEMPLATE`**（避免纯文本路径 prompt 回归）。
   - `_classify_once(..., vision_images)`：有图时 user content = `[{"type":"text","text":user_message}, *image_parts]`，否则维持 str。
   - **失败兜底（鲁棒性核心）**：当本次请求携带图片且发生**请求级失败**（异常 / 空 choices）→ WARNING + `announcements.announce("vision_fallback", "warning", …)`（提示检查模型/端点是否真支持图片），并**同批立即一次纯文本重试**（去掉 image parts 重发）；重试成功 → `revoke` 公告并按正常流程解析。携带图片的请求成功 → `revoke("vision_fallback")`。解析失败/`finish_reason=length` 拆半等**内容级**失败不触发兜底（与图片无关，维持既有语义）。此兜底保证「配置误开 vision」不会陷入每轮回填重试的永久死循环。

7. **`briefdesk/pipeline.py`**（配置组合守卫）
   既有 `not enrich_stages` 分支（:155-173）旁：若 `config.ai_vision_enabled` → WARNING 日志 + `announcements.announce("vision_without_ocr", "warning", …)`（提示需在 PLUGINS 启用 ocr 才能把图片送入模型）。announce 内容不变不重发，天然防刷屏。

8. **`briefdesk/plugins/ai_provider/engine.py`：不改代码**（chat 已透传 parts）。仅在文档陷阱小节记录：`_use_json_object` 与图片共存的边界（ollama json 模式兼容图片；deepseek 文本模型不会开 vision；若某端点拒绝该组合，请求级失败会触发第 6 条兜底）。

9. **`.env.example`**：新增 `AI_VISION_ENABLED` / `AI_VISION_MAX_IMAGES` 两项带注释。

## 四、鲁棒性清单

- 开关默认 false = 字节级现状；无图消息即使 vision 开启也走纯 str content。
- 图片护栏：单图缩放归一（≤1568px JPEG，典型 100-400KB）、单条上限 4、单请求预算 12、解码失败逐图跳过、下载失败逐条跳过——任何一层失败都只降级为该条纯文本，不拖垮批次。
- 内存上界：回填批 10 条 × 4 图 × ~400KB ≈ 16MB 瞬时/批，批结束即弃。
- 请求体上界可控（12 × ~530KB base64 ≈ 6MB），避免打爆端点请求限制。
- vision 误配自愈：请求级失败同批纯文本重试 + 常驻公告条提示，不产生永久回填死循环。
- `items.image_urls`、dedup 图片短路、`[OCR]` 契约、上下文回填剥标记、QR 噪声清洗等下游全部不受影响；DB schema 零变更。
